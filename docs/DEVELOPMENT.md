# Development notes — Last Folder Standing

What this file is: how to work in this repo. See README.md for the product itself.

## Repo layout

```
src/common/              Header-only helpers shared by all three binaries: JSON,
                         file and settings I/O, string and time conversion, the
                         CLSID. No dependencies beyond the standard library.
src/LFS.Monitor/         C++ (Win32) background process + tray icon.
                         Watches MRU sources, writes state.json. ALL logic lives here.
src/LFS.ShellExtension/  C++ COM in-proc DLL. Namespace extension pinned to nav pane.
                         Renders state.json. NO business logic. Must never crash Explorer.
src/LFS.Settings/        C++ (Win32) settings window, resource dialog, 2 settings.
src/tools/shellext_probe/  Dev-only harness that drives the extension without
                         Explorer. Never shipped; run it before every registration.
assets/app.ico           Generated by tools/make_icon.ps1, committed.
installer/               Inno Setup script. Registers COM DLL, autostarts monitor.
docs/                    Architecture notes, MRU format notes.
PLAN_01_monitor.md       Implementation plan: monitor process
PLAN_02_shell_extension.md  Implementation plan: namespace extension
PLAN_03_settings_installer.md  Implementation plan: settings UI + installer
```

Work through the plans in order. PLAN_01 is fully testable standalone (console output
mode) before any shell code exists.

## Hard rules

1. **The shell extension is dumb.** It reads `%LOCALAPPDATA%\LastFolderStanding\state.json`
   and renders it. It never touches the registry MRU, never parses PIDLs from the MRU,
   never does I/O beyond state.json + a change notification on that directory.
   Rationale: this DLL is loaded into explorer.exe and into every process that shows a
   file dialog. A crash here crashes the host app. Keep the surface minimal.
2. **No hooks.** No SetWindowsHookEx, no API detours, no DLL injection. Sources are
   registry MRU + Recent folder only. This is a hard product decision (AV false
   positives, PowerToys eligibility).
3. **Monitor must survive malformed input.** MRU PIDLs can be garbage, .lnk files can
   point to deleted/unreachable targets (network shares!). Never block on target
   resolution — resolve .lnk without network access flags, drop entries that fail.
4. **state.json is the only contract** between monitor and shell extension. Schema
   changes require bumping `"version"` and keeping the extension backward compatible.
5. Language: C++20 throughout (MSVC, /W4 /WX). No CLR in the shell extension —
   .NET namespace extensions are unsupported by MS.
   The settings window was planned as C# / WinUI 3. It is plain Win32 instead:
   WinUI 3 needs the Windows App Runtime on the target machine, which means
   either a ~60 MB self-contained payload or a machine-wide runtime install that
   asks for admin. Both break the per-user, no-admin promise for a window with
   two settings. It is a resource dialog in src/LFS.Settings, ~110 KB.

## state.json schema (v1)

```json
{
  "version": 1,
  "updatedUtc": "2026-08-28T10:15:00Z",
  "folders": [
    { "path": "C:\\Users\\stef\\Documents\\Mixes", "lastUsedUtc": "2026-08-28T10:14:58Z", "source": "opensave" },
    { "path": "D:\\Samples\\Kicks", "lastUsedUtc": "2026-08-28T09:02:11Z", "source": "recent" }
  ]
}
```

`folders` is already sorted (newest first), deduped, exclude-filtered and truncated to
maxFolders by the monitor. The extension renders it verbatim.
`source` is one of `opensave`, `lastvisited`, `recent`.

## settings.json schema (v1)

`%LOCALAPPDATA%\LastFolderStanding\settings.json`

```json
{
  "version": 1,
  "maxFolders": 5,
  "excludePaths": ["%TEMP%", "*\\node_modules\\*"]
}
```

Environment variables are expanded, matching is case-insensitive against the full path.
A pattern containing `*` or `?` is matched as a glob; a pattern without wildcards
excludes that folder **and everything below it**, which is what people expect from
entering a plain folder path.

## Build & test

- Build: VS 2022, x64 only. `build.ps1` at repo root builds everything.
  `.\build.ps1 -Config Release`, `.\build.ps1 -Config Release -Installer`, `.\build.ps1 -Clean`.
- Monitor test modes (neither writes state.json):
  - `--console` — run the pipeline and print each result, keep watching. `--once` for a
    single pass.
  - `--dump` — print every raw source entry with group, rank and timestamp *before*
    filtering. First thing to reach for when the list looks wrong.
- **Shell extension: run `shellext_probe.exe` before you ever register the DLL.**
  It loads the DLL directly and drives it through the whole IShellFolder2 surface,
  including deliberately malformed PIDLs. A crash there is a crash in explorer.exe
  later. `shellext_probe.exe --registered` additionally checks that the node shows
  up in the desktop's `SHCONTF_NAVIGATION_ENUM` — which is what the navigation pane
  itself enumerates — and requires the DLL to be registered.
- Registering by hand: `regsvr32 /s LFS.ShellExtension.dll` (HKCU, no admin),
  `regsvr32 /u /s ...` to undo. Be ready to unregister from a cmd window if Explorer
  ever crash-loops.
- Note: once Explorer has loaded the DLL it keeps it mapped, so a rebuild fails with
  a locked file until Explorer unloads it (minutes) or restarts.
- Verify dialog integration with Notepad's Open dialog (simplest common-dialog host).
- Icon: `tools\make_icon.ps1` regenerates `assets\app.ico`. Only run it when the icon
  should change; the result is committed and stamped into all three binaries by CMake.

## Conventions

- Direct, terse commit messages, English, imperative ("Add PIDL decoder for OpenSavePidlMRU")
- No tooling references in commits or in anything published to GitHub
- Each PLAN file has a checklist at the bottom; tick items off as you complete them
- No dependency on anything that requires admin at runtime; installer may elevate once
